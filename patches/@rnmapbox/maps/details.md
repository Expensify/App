# `@rnmapbox/maps` patches

### [@rnmapbox+maps+10.3.10+001+immediate-follow-camera-transition.patch](@rnmapbox+maps+10.3.10+001+immediate-follow-camera-transition.patch)

- Reason: Removes the long "fly-in from space" animation that plays the first time a `Camera` with `followUserLocation={true}` engages follow mode (used by `GPSMapView` on the GPS distance screen). When entering follow mode, `@rnmapbox/maps` calls the Mapbox viewport transition with no explicit transition argument, so the SDK uses its `DefaultViewportTransition`, which animates from the current camera (world view / zoom ~0) all the way in to the user. Because the JS layer discards `defaultStop`/`stop` while `followUserLocation` is true (`src/components/Camera.tsx`), there is no JS-only way to seed the start position or pick an animation mode — the only lever is the native transition itself.
- Solution: Adds an opt-in `followUserLocationUseImmediateTransition` prop to `Camera`. When `true`, entering follow mode uses `makeImmediateViewportTransition()` so the camera snaps straight to the follow state. When `false` (default), upstream behavior is preserved and the default viewport transition animates. `GPSMapViewContent` turns the prop on for the initial map load (no route yet, or GPS tracking in progress) and clears it from `Viewport.onStatusChanged` only once the transition to `followPuck` succeeds, so a failed first attempt (no location fix yet) also retries immediately. Later re-engagements (center button, follow after clearing a route) pass `false`, so the camera animates back to the user.
- Files changed:
  - `src/specs/RNMBXCameraNativeComponent.ts` and `lib/module/specs/RNMBXCameraNativeComponent.ts` — new `OptionalProp<boolean>` in the codegen spec. Codegen turns it into the native props field and, on Android, the `setFollowUserLocationUseImmediateTransition` method of `RNMBXCameraManagerInterface`.
  - `src/components/Camera.tsx` and `lib/typescript/src/components/Camera.d.ts` — new field on `CameraFollowConfig`, passed through to the native component.
  - `lib/module/components/Camera.js` — same prop pass-through in the compiled bundle. Since 10.3.2 the package has no `react-native` source entry and its exports map falls back to `lib/module`, so Metro bundles the compiled output, not `src`.
  - iOS — `ios/RNMBX/RNMBXCameraComponentView.mm` reads the prop in `updateProps`, and `ios/RNMBX/RNMBXCamera.swift` stores it and picks the transition in `_updateCameraFromTrackingMode`.
  - Android — `RNMBXCameraManager.kt` adds the `@ReactProp`, and `RNMBXCamera.kt` stores it and picks the transition in `_updateViewportState`. Like the other follow props, the setter re-runs `_updateViewportState()`, so clearing the flag after a successful snap re-enters follow mode with the default transition. The camera is already on the user at that point, so nothing visibly moves. On iOS the property has no `didSet` and is only read the next time follow mode is entered.

- 10.3.10 port: the logic is unchanged, only the surrounding code moved.
  - Upstream now calls `cameraWillMoveMap()` right before the follow transition ([rnmapbox/maps#4371](https://github.com/rnmapbox/maps/pull/4371)). It notifies native code outside the package that `<Camera>` is about to move the map. Nothing in the package or in App listens to it. The immediate-transition branch sits after that call, so the notification fires for both the immediate and the default transition.
  - On iOS, `_updateCameraFromTrackingMode` now goes through the Mapbox `mapView` for the viewport (`makeFollowPuckViewportState`, `addStatusObserver`, `setCamera`) and keeps `map` only for `cameraWillMoveMap()`. The patched lines follow suit: `map.viewport.transition(...)` became `mapView.viewport.transition(...)`.
  - Everything else only shifted line numbers. `RNMBXCameraManager.kt` and both `RNMBXCameraNativeComponent.ts` specs are unchanged upstream.
